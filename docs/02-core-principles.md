# Core Principles

## 1. Ordinary Language In, Structured Product Out

The user may describe intent with rough, emotional, incomplete, or non-technical language. The system must translate it into product and engineering structure.

The translation must preserve uncertainty. If the user's words imply multiple possible products, the system must say so.

## 2. Deduce Before Asking

Do not ask generic intake questions when the answer can be inferred safely.

Ask questions only when the answer changes the product trajectory, risk profile, architecture, cost, or autonomy level.

## 3. Challenge Before Building

Ambitious or ambiguous work must pass a challenge gate. The challenge should be plain-language, specific, and useful. It should not become a bureaucratic wall.

## 4. Premium Means Trust

Premium means clarity, reliability, configurability, cost awareness, and honest limits. Decorative polish cannot compensate for fake status, broken flows, or hidden risk.

## 5. Separate Experience From Control

Every serious product needs an Experience Plane UI and a Control Plane UI. Mixing user workflows with logs, internal workers, queue states, and admin controls creates confusion and false quality.

## 6. Everything Connectable, Nothing Entangled

Capabilities should declare their inputs, outputs, events, artifacts, costs, risks, and relations. They should not depend directly on every other module.

Use contracts, events, typed artifacts, registries, and context loading instead of implicit coupling.

## 7. Cost Is A Product Constraint

Token cost, API cost, runtime, cacheability, human review cost, and maintenance cost are part of the product. A premium system spends depth where it matters.

## 8. Autonomy Must Be Observable

Autonomous work must leave traces: status, logs, artifacts, decisions, tests, failures, and final reports. No worker should be trusted only because it says it succeeded.

## 9. Safety Zones Are Mandatory

Green actions may be autonomous. Orange actions require proposal and review. Red actions require explicit human approval.

## 10. Feedback Updates The Right Layer

Not every comment rewrites the North Star. Feedback should be reformulated, classified, mapped to affected layers, converted into tasks, tested, and documented only where needed.
